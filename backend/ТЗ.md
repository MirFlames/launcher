## Техническое задание (backend): сервис автообновления лаунчера

### 1. Назначение
Backend-сервис предоставляет лаунчеру информацию о требуемой версии клиентских файлов/модов и ссылки для их загрузки. Лаунчер сравнивает локальные файлы с эталонными по SHA-256 и при необходимости скачивает файлы по предоставленным URL.

Источник требований: текущая реализация клиента в `MinecraftLauncher/MinecraftLauncher/GameUpdater.cs` и модель `MinecraftLauncher/MinecraftLauncher/Models/ServerInfo.cs`.

---

### 2. Общая схема работы (как ожидает лаунчер)
- Лаунчер выполняет запрос `GET /api/version`.
- В ответ получает JSON (см. раздел 4) с:
  - целевой версией Minecraft (`minecraft_version`);
  - списком файлов клиента (`client_files`);
  - списком модов (`mods`);
  - опциональным агрегированным хешем модов (`mods_hash`) — клиент сейчас его не использует, но поле обязательно в JSON-контракте.
- Для каждого элемента из `client_files` и `mods` лаунчер:
  - скачивает файл по полю `url` (HTTP GET), ожидая наличие `Content-Length` для расчёта прогресса;
  - сохраняет файл в локальную структуру директорий (см. раздел 3);
  - вычисляет SHA-256 и сравнивает со значением `hash` из ответа.

---

### 3. Локальная структура установки (важно для требований к `name`)
Лаунчер кладёт файлы в каталог:
`%APPDATA%\.minecraft_custom`

#### 3.1. Клиентские файлы
Путь сохранения каждого файла из `client_files`:
`%APPDATA%\.minecraft_custom\versions\<minecraft_version>\<name>`

#### 3.2. Моды
Путь сохранения каждого файла из `mods`:
`%APPDATA%\.minecraft_custom\mods\<name>`

#### Требование к полю `name`
- `name` должен быть **относительным** путём/именем файла без выхода из целевого каталога (запрет `..`, абсолютных путей, UNC-путей и т.п.).
- Допускаются подкаталоги (например `libraries\xxx.jar`) только если это действительно нужно и не приводит к path traversal.

---

### 4. API

#### 4.1. Получение манифеста версии
**Endpoint:** `GET /api/version`  
**Назначение:** вернуть манифест (какие файлы должны быть у клиента и где их скачать).

##### 4.1.1. Успешный ответ
**HTTP 200**  
**Content-Type:** `application/json; charset=utf-8`

**JSON-структура (строго по контракту клиента):**
- `minecraft_version` (string) — версия (используется как имя папки в `versions`).
- `mods_hash` (string) — строка (может быть пустой). Клиентское приложение поле сейчас не использует, но ожидает в модели.
- `client_files` (array of objects) — список файлов клиента:
  - `name` (string) — относительное имя/путь файла (см. раздел 3).
  - `url` (string) — прямой URL для скачивания файла (HTTP/HTTPS).
  - `hash` (string) — SHA-256 файла в hex-формате.
- `mods` (array of objects) — список модов:
  - `name` (string) — имя/путь файла мода (см. раздел 3).
  - `url` (string) — прямой URL для скачивания файла (HTTP/HTTPS).
  - `hash` (string) — SHA-256 файла в hex-формате.

**Требование к `hash`:**
- Алгоритм: **SHA-256**.
- Формат: **hex** без разделителей, длина 64 символа.
- Регистр: допускается любой, но рекомендуется отдавать **в нижнем регистре**, т.к. клиент приводит обе стороны к lower-case при сравнении.

##### 4.1.2. Ошибки
Клиентская реализация при любой ошибке запроса/десериализации:
- пишет сообщение в консоль;
- считает, что версии получить не удалось (возвращает `null`).

Поэтому backend должен:
- возвращать **валидный JSON** по контракту;
- использовать корректные HTTP-коды.

Минимальные коды:
- **200** — успех.
- **5xx** — внутренняя ошибка (в этом случае клиент не сможет обновиться).

---

### 5. Раздача файлов (download URLs)
Так как лаунчер скачивает файлы по `url`, backend обязан обеспечить доступность этих URL.

#### 5.1. Требования к скачиванию
- HTTP метод: **GET**.
- Сервер должен поддерживать выдачу бинарного содержимого.
- Должен быть заголовок **`Content-Length`** (иначе прогресс в клиенте не рассчитывается).
- URL должны быть **доступны извне** и отдавать актуальный файл, соответствующий `hash`.

#### 5.2. Рекомендации (не обязательные для работы текущего клиента)
- HTTPS (для защиты от MITM).
- `ETag` / `Last-Modified` (кэширование).
- `Accept-Ranges: bytes` (докачка при обрывах) — клиент сейчас не использует, но полезно.

---

### 6. Консистентность данных (обязательное)
- Для каждого элемента в `client_files` и `mods`:
  - `url` обязан указывать на файл, чей SHA-256 **строго совпадает** с `hash`.
  - `name` должен соответствовать ожидаемому имени при сохранении (см. раздел 3).
- `minecraft_version` не должен содержать символов, запрещённых в именах папок Windows (`<`, `>`, `:`, `"`, `/`, `\`, `|`, `?`, `*`) и не должен быть пустым.

---

### 7. Нефункциональные требования
- **Доступность**: endpoint `/api/version` должен отвечать быстро (рекомендуемо до 1–2 секунд).
- **Таймаут клиента**: клиент ждёт ответ до ~5 минут (но это верхняя граница; фактически ответ должен быть значительно быстрее).
- **Обратная совместимость**: изменения контракта JSON недопустимы без синхронного обновления клиента.
